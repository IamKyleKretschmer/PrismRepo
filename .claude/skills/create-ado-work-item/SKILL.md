## Overview

This agent creates Azure DevOps Product Backlog Items (PBIs) from feature specifications.

You can either:
- Create work items from an existing feature in `/specs/` (with spec.md and tasks.md)
- Create a work item from a direct description provided by the user

## Pre-Execution Setup

1. **Load shared configuration**: Read `/.prism/config/work-item-parameters.yml` for organization, defaults, prefixes, tags, and link types.

2. **Check for Azure DevOps MCP tools**: Search for available Azure DevOps MCP tools using tool_search if not already loaded.
   - If available, prefer using MCP tools to create work items directly
   - If not available, generate markdown-formatted work item drafts for manual creation

3. **Determine context**:
   - If the user references a feature in `/specs/`, read its `spec.md` and `tasks.md`. `tasks.md` is
     an **index**: follow each link to the task file in `/specs/{feature-name}/tasks/`, which holds
     the authoritative definition (objective, scope, contract, acceptance criteria, testing
     requirements, `repository`, `story`, `effort`). A feature with no `tasks/` directory predates
     this layout — read the definitions inline from `tasks.md` instead.
   - If the user provides a direct description, use that as the source
   - Check if `spec.md` contains `azure-devops-parent-feature-id` in YAML frontmatter for parent linking

## Work Item Generation Rules

Follow these rules for every work item:

1. **Work Item Type**: Create `Product Backlog Item` only. Do not create Azure DevOps `Task` work items.

2. **Title Format**: Prefix titles using `repositoryTitlePrefixes` from the configuration based on the repository each work item targets.
   - Example: "Tables API - Add changes field to data-row-updated event"
   - If no repository is specified or multiple repositories are involved, omit the prefix

3. **Tags**: Apply the following tags to every work item:
   - `tags.common` (e.g., "Data Tables")
   - `tags.aiGenerated` (e.g., "Generated by AI")
   - Repository-specific tags from `tags.repositorySpecific` when a repository mapping exists

4. **Standard Fields**: Set from the shared configuration:
   - **Area Path**: `azureDevOps.areaPath`
   - **Iteration Path**: `azureDevOps.iterationPath`
   - **Work Type Budget**: `defaults.workTypeBudget`
   - **Priority**: `defaults.priority`
   - **Value Area**: `defaults.valueArea`
   - **Effort**: Choose from `defaults.effortValues` (Fibonacci sequence) and mark as `(agent estimate)`

5. **Description Format**: Structure the description as follows:
   ```markdown
   ## Source
   
   [Feature Tasks]({organisationUrl}/_git/{specsRepository}?path=/specs/{feature-name}/tasks.md)

   <!-- When the PBI maps to specific task files, link them too: -->
   [T014 Add note history endpoint]({organisationUrl}/_git/{specsRepository}?path=/specs/{feature-name}/tasks/T014-add-note-history-endpoint.md)
   
   ## Overview
   
   {Brief description of what this work item achieves}
   
   ## Requirements
   
   {Relevant requirements and implementation details from spec and tasks}
   
   ## Acceptance Criteria
   
   - [ ] {Criteria derived from spec and task definitions}
   - [ ] {Additional criteria as needed}
   
   ## Definition of Ready
   
   - [ ] Requirements are clear and testable
   - [ ] Dependencies are identified
   - [ ] Acceptance criteria are defined
   - [ ] Technical approach is understood
   - [ ] Estimated effort is reasonable
   
   ## Notes
   
   {Any additional context, constraints, or coordination requirements}
   ```

6. **Links**:
   - If a parent feature ID exists (`azure-devops-parent-feature-id` in spec.md frontmatter), create a parent link using `linkTypes.parent`
   - Link related work items using `linkTypes.related` where task dependencies indicate relationships

## Execution Steps

1. **Parse User Input**: Extract the feature description, repository targets, and any specific requirements.

2. **Load Configuration**: Read and parse `/.prism/config/work-item-parameters.yml`.

3. **Identify Repositories**: Determine which repository(ies) the work involves based on:
   - Explicit mentions in the user input
   - Feature context if working from `/specs/`
   - Nature of the work described

4. **Generate Work Item(s)**:
   - For each logical unit of work, create one PBI. From a feature, the unit is the **user story** —
     one PBI per story, listing that story's task titles and links as bullets in the Description
   - Apply the title prefix from the `repository:` field of that story's task files
   - Set all required fields from configuration; prefer the task files' `effort:` values, summed
     per story, over a fresh estimate
   - Format the description with all sections
   - Include acceptance criteria that are specific and testable — derive them from the
     **Acceptance Criteria** and **Testing Requirements** sections of the story's task files

5. **Create or Draft Work Items**:
   - **If Azure DevOps MCP tools are available**: Use them to create work items directly in Azure DevOps
     - Important: Set `Custom.WorkTypeBudget` field to the value from `defaults.workTypeBudget` in the configuration
   - **If MCP tools are not available**: Generate markdown-formatted work item specifications for manual creation

6. **Output**:
   - Provide the work item ID(s) if created via MCP
   - Provide formatted work item text if drafted for manual creation
   - Include a summary of what was created
   - Note any missing information that requires user input

## Validation Rules

Before finalizing work items:

- ✅ Title includes the correct repository prefix (if applicable)
- ✅ All required tags are applied
- ✅ Effort is selected from the configured Fibonacci values
- ✅ Area and Iteration paths match the configuration
- ✅ Acceptance criteria are specific and testable
- ✅ Description includes the source link (if from a feature)
- ✅ Parent link is created if parent feature ID exists
- ✅ Related links are created where dependencies exist

## Error Handling

- If the parent feature ID or other required feature data is missing, **stop and ask** rather than inventing values
- If no repository-specific prefix or tag exists for a target repository, use only the shared defaults that are explicitly configured
- If the configuration file is missing or malformed, report the error and do not proceed
- If MCP tools fail, fall back to generating markdown drafts

## Example Execution

For the user request:
> "Create an ADO work item to add a 'changes' field to the data-row-updated event in Tables API"

**Steps**:
1. Load configuration from `/.prism/config/work-item-parameters.yml`
2. Identify repository: `ntx-tables-api`
3. Apply prefix: "Tables API -"
4. Create PBI with:
   - Title: "Tables API - Add changes field to data-row-updated event"
   - Tags: "Data Tables", "Generated by AI"
   - Effort: 5 (agent estimate)
   - Description with requirements, acceptance criteria, and notes
5. Output the created work item or draft

## Post-Execution

After creating work items:
- Provide a summary of what was created
- Include links to the created work items (if using MCP)
- Suggest next steps (e.g., review, refinement, adding to sprint)
